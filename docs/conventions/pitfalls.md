# 踩坑手册（pitfalls）

> **收录标准**：只收「会再踩且带规避动作」的坑。每条固定四段式：**坑 → 症状 → 根因 → 规避**。一次性事故流水账不收。
> **用法**：接到怪问题先来这里查有没有人踩过；踩了新坑且符合收录标准的，修复后追加条目。
> 条目按域分组：出题域（AI 出题流水线）/ App 域（Compose 代码）/ 工具与流程域。

---

## 一、出题域

### 1.1 答案键与运行输出矛盾（batch-0004-Q4、batch-0005-Q9 两次同型）

- **坑**：正确选项的文字描述与程序实际输出不一致（如选项写 `收到 [0,5]`，程序实测打印 `0、5、6`）。
- **症状**：盲答全对、冷复审也全对，但把选项文字和运行输出并排一放就穿帮——两次都是维护者侧机械验证抓出来的。
- **根因**：复审方语义上知道题目考什么，**字面校对失守**；出题方手抄题干代码时「顺手修正」（补 import、改短名）会掩盖真实行为。
- **规避**：代码块从 JSON **机械提取**再编译运行（不手抄）；验证必含「运行输出 vs 选项文字逐字比对」这一环。

### 1.2 答案键与解析自相矛盾（batch-0005-Q11、batch-0007 返工中两次出现）

- **坑**：多选答案键漏选、或改了题干/选项忘了同步答案键（题干为真、答案为假）。
- **症状**：解析整段论证「B 也不推荐」，答案键却没有 B；学习者按解析选会被判错。
- **根因**：返工只改一处、没做全量一致性核对。
- **规避**：交付前机械核对「解析『为什么选 X』与答案键一致」（selfcheck 脚本四类检查之一）；改任何一处后全量重跑。
- **2026-10-05 起已机械拦截**：本条从「靠脚本／人眼核」升级为**应用级规则 9 与 10**（权威源 `docs/schema/batch-spec-v1.md`，两端实现 + `app-level-fixtures.json` 共同夹具钉住）。触发源是 **batch-0024-Q7 的真实缺陷**：解析写「A 整体是错误项、不入选」而 `answer` 含 A——该形态就是「多选全选」，由规则 9 拦；规则 10 另拦「解析显式声明的答案与 `answer` 脱钩」（实测 249 道选择题中 101 道有声明）。
- **反面记录（别再试）**：「按关键词近邻判解析是否说某字母不入选」这条路**实测不可靠**——26 个真实批次、249 道选择题，命中 4 处，**4 处全是误报**。中文散文可以否定（`不选 X`）、可以引用（`…的断言是错的`）、可以把「排除」安在**别的**选项上（窗口里同时出现 `坐实了 B 的必要性` 与 `C 不选`）。判据只能是**确定性的外在形态**（规则 9）或**结构化习语 + 否定守卫 + 按题型分档**（规则 10）。

### 1.3 探针多选项通过时，该改题型而不是硬定答案（batch-0006-#12）

- **坑**：编译探针实测 C、D 都能通过，却因「单选必须只有一个答案」硬把答案定成 C。
- **症状**：证据就在自己的终端输出里，仍然视而不见。
- **根因**：机械链路只覆盖「运行输出 vs 选项文字」，没覆盖「探针结果 vs 题型选择」。
- **规避**：多个选项同真时，正确反应是**改成多选**；机械检查应含「探针结果 vs 题型」比对。

### 1.4 页面级事实是易逝事实（batch-0006-Q10）

- **坑**：题干引用「官方分类表」，官方页面改版后章节消失，题目变幽灵——学习者核查会扑空。
- **症状**：当前官方页面找不到题目所引用的结构；甚至不同时间抓取结果不同（CDN 波动/回滚）。
- **根因**：把「某版页面的章节结构」当成了永久事实。
- **规避**：引用官方页面须**绑时点**（题干写明版本/日期）+ 解析附 **Wayback 快照链接**；实现细节（线程数、默认值等）不进题干，只考定性结论。

### 1.5 时序竞争不能当契约（batch-0005 `sample`、batch-0006 `flatMapMerge`）

- **坑**：把并发竞争产生的具体输出顺序（`[11,21,31,...]`）或时序敏感结果（`sample(60ms)` 得 `[2,4,6,8]`）写成答案。
- **症状**：同一程序多次运行输出不同；复审方探针出竞态误判。
- **根因**：非确定性结果被当成确定性契约。
- **规避**：非确定输出只考**性质**（「顺序不保证」「会静默」），不考具体序列；验证端用阻塞握手而非 `delay`/`tryReceive` 赌时序。

### 1.6 伪变式：仅改数字/变量名/措辞不算变式

- **坑**：把 `delay(1000)` 改 `delay(2000)`、`map { it * 2 }` 改 `it * 3` 就当新题。
- **症状**：刷题者体感「这题做过」；批次题量上去了、考点没增加。
- **根因**：旧规范「一题一考点、不重复」把出题 AI 逼向「安全地换皮」。
- **规避**：变式须满足换题型/换考核角度/换场景载体至少一条（规范 §二.2）；每个核心考点出 2–4 道变式，考点清单须列与历史批次的重叠及本次角度。

### 1.7 填空题答案必须覆盖书写变体

- **坑**：`acceptableAnswers` 只写一种写法（如 `0`），用户答 `零` 被判错。
- **症状**：导入判分误伤。
- **根因**：没从答题者视角枚举等价写法。
- **规避**：至少覆盖三类（`@FlowPreview` / `FlowPreview` / `flow-preview`；`0` / `零`）。

### 1.8 解析里的「本机实测」数字也必须真跑，且数量级要自洽（batch-0008 两轮）

- **坑**：答案键与程序输出全对，但解析正文中编造/误传实测数字：「`1*2^32` 溢出成 2147483647」（int 环绕实测为 0，该数是 2³¹−1）；「200 万次随机验证，不等 29,982,488 次」（事件次数大于试验次数，算术矛盾）；「`-7 & 0xFFFFFFFF` 抹掉符号位」（int 域是 no-op，实测仍为 -7）。
- **症状**：盲答 12/12、冷复审全过，维护者探针一跑就穿帮；学习者照解析自己验证必然扑空。
- **根因**：机械验证只覆盖「题干程序 → 选项文字」，没覆盖「解析佐证数字 → 复现实验」；绑定「本机实测」字样给了虚假的可信感。
- **规避**：解析中每一个数字断言都要能被独立复现；自写探针不仅验题干，还验解析里的延伸实验；数量级先过常识关（事件次数 ≤ 试验次数）。

### 1.9 返工脚本整段赋值会清空解析（batch-0008 事故）

- **坑**：本意是替换解析中的一个小节，脚本却写成 `explanation = 新值` 整段覆盖，而新值只是其中一节——「为什么对/为什么错」全段消失（1241 → 667 字符）。
- **症状**：返工点改对了，解析主体被抹掉，违反必写段要求。
- **根因**：脑补了工具语义——把「整段赋值」当「替换其中一节」，与 1.1「复制代码时顺手改」同型。
- **规避**：改 JSON 文本一律用**精确字符串替换 + 命中数断言**（命中 0 或 >1 即非零退出）+ 改后必写段长度检查；禁止对 explanation 整段赋值。

### 1.10 U+FFFD 替换字符只能机器扫，眼睛会自动把它读成正常汉字（batch-0009 Q6）

- **坑**：解析里混入 U+FFFD 编码损坏字符（`不��限定词`，本应为「不带限定词」）；batch-check 与 selfcheck 都不管非法替换字符，通读自查也没发现——人眼会把残缺处脑补成正确的字。
- **症状**：批次在所有校验下通过，但学习者 App 里看到死字符；且损坏可能同时存在于**生成器源码**，只改产物、下次重跑生成器又原样回来。
- **根因**：编码/复制链路丢字节产生 U+FFFD；检查清单里没有「非法字符」这一维，注意力检查对自己打字/粘贴造成的损坏无效。
- **规避**：selfcheck 加一条**全文 + 逐字段扫描 U+FFFD（`chr(0xFFFD)` 构造，勿在脚本里写字面死字符）**，命中即非零退出并打印题号上下文；生成器与产物一起扫，修损坏要同时修源头。

### 1.11 「为真但缺一个限定条件」——版本、页面、前提三件套（batch-0009 四次翻车三次同病）

- **坑**：句子本身可能为真，但经不起追问：引的官方措辞已过期（JDK 8 删除的话）、指错页面（`ReferenceQueue` 行为写到包说明页）、或因果链想当然（HashMap 去重失败归因「不同桶」，实测同桶不同 hash 也失败、真因是桶内先比 hash 短路不调 equals）。
- **症状**：答案键正确、数字也对，但解析的机制/出处一核验就塌；默认容量下的巧合（hash 1/17 在 32 槽恰好异桶）让错误因果显得天衣无缝。
- **根因**：把「常见教材的说法」「特定配置下的现象」当成无条件机制陈述。
- **规避**：凡写「官方说 X」必须同时钉死**在哪个版本（JDK N）、哪个页面（具体 javadoc/JLS 节）、什么前提下（容量/存活率等）**；机制类断言换一个配置（如 HashSet 初始容量）复现，巧合就暴露。

### 1.12 并发计数的方向断言是 `≤` 不是 `<`（batch-0010-Q8）

- **坑**：无同步自增计数器的终值写成「必然**小于**期望值 / `plainValue < EXPECTED` 恒真」，选项却又承认「某些运行可能恰好相等」——自相矛盾。
- **症状**：本地多次运行恰好都偏小（高竞争下相等是小概率），让 `<` 看起来恒真；跨机复现即可出现相等。程序打印的布尔行 `< EXPECTED` 在那些运行里输出 `false`，与「恒真」结论冲突。
- **根因**：丢失更新只会让结果**偏小或相等**，不会偏大——方向上界是 `≤`；把"通常偏小"提升成"严格小于"是过度断言。并发断言尤其不能拿"我这边 N 次都没碰上"当恒真证据（pitfalls 1.5）。
- **规避**：并发题断言方向时先问「一次更新都不丢时等号成不成立」，成立就是 `≤`/`≥` 不是 `</>`；判据要 API 契约或数学论证背书，不靠跑很多轮没碰到反例。

### 1.13 返工半途而废：发现了事实却没沿它推到底（batch-0010-Q8 二轮）

- **坑**：第一轮已发现「某些运行恰好相等」，改了选项 B 的措辞，却没往上推到题干那行 `plainValue < EXPECTED` 和解析里的「恒真」——只改了一处，同一矛盾留在另外两处。
- **症状**：表面「已经修过了」，但题干/选项/解析三处仍互相打架；比没发现更难被发现，因为最新一版看起来回应了意见。
- **根因**：把返工当成「改掉被点名的那句」，而不是「按新事实把所有受影响的位置一起重推」。
- **规避**：返工的触发点是一个**事实变化**时，用 grep 把该事实的全部落点（题干输出、每个选项、解析各段）列出来逐个改，再做一次跨字段一致性自检；selfcheck 增加「同句跨字段矛盾」检测（本批代理已补）。

### 1.14 验证时的「跑 N 轮」写成了「启动 N 个 JVM」（2026-10-05，一次弹出数百个 java 控制台窗口）

- **坑**：为测不稳定行为，把「同一段程序跑 N 轮 × M 个变体」直接写成 N×M 次 `java Xxx.java` 启动（实测一次 6 题 × 30 轮 × 2 变体 = 360 次）。
- **症状**：屏幕上连续弹出几百个 java 控制台窗口抢焦点（用户原话：「老有一个 java 的终端弹出」），机器被拖慢；更麻烦的是长驻探针（多线程等待类）不退出，事后留下挂住的 `java.exe`（见到过一个存活约 10 分钟）。
- **根因**：把「跑 N 轮」理解成「启动 N 次」——轮次是**程序内部**的事，与进程启动次数无关；且未给可能死锁的探针加看门狗，未在收尾自查残留进程。
- **规避**（已写进 §二.5 进程调用纪律）：① N 轮写成**一个程序里的 `for` 循环**，全程只启 1 个 JVM（360 次 → 6 次）；② 分流用 `java -Xmx256m Xxx.java 1>out.txt 2>err.txt` **一次调用**同时拿两个流，不要为分流跑两遍；③ 后台跑用 `Start-Process java -NoNewWindow`；④ 可能死锁的探针必须加看门狗（超时打印状态后硬 `System.exit(0)`）；⑤ 收尾自查残留 java 进程。

### 1.15 立「篇幅/体量」口径时漏了「选项」，产物整批返工（2026-10-05 全库重排）

- **坑**：为「碎片时间刷题」立篇幅硬线时，只圈了**题干（含代码）**与**解析**，**漏掉选项文本**。
- **症状**：第一轮 4 批按该口径全部"达标"、`batch-check` 也 0 错误，之后才发现选项仍是 4×60–140 字——选项是**每题作答都要读**的文字，漏掉它等于口径只解决了一半；补上「单选项 ≤60 字」后这 4 批**全部回头返工**。
- **根因**：把「篇幅」默认等同「题干 + 解析」，没有清点**用户为作答必须读到的全部文字**。
- **规避**：立「体量/篇幅」类口径时，先列全"每次作答要读的字"清单（题干 / 选项 / 解析 / 解析里的代码），逐项定线；产物生成前拿**极值样本**（最长题干、最长选项）人工过一眼，别等机械校验说"达标"就当结束。

### 1.16 「达标」是相对某条口径说的——换口径后必须全量重跑（2026-10-05 全库重排）

- **坑**：批量改写时把「看起来已达标」的短批（`batch-0001`/`batch-0002`，最长题干 57/115 字）跳过机械校验。
- **症状**：全量重跑 `batch-check` 后暴露它们**用了冻结标签 `basics`**——这是**词表口径**下的违规，与篇幅无关；"没改内容"≠"无需校验"。
- **根因**：把"这批没改"当成"这批没问题"，而违规面可能来自**另一个维度**的口径。
- **规避**：每轮改动后对**全部**批次重跑一遍 `batch-check`，别只跑"看起来有问题"的；写结论时说清"相对哪条口径达标"。

### 1.17 解析替官方下的「全称结论」必须逐字回官方页核，且要查同站其它页（2026-10-05 全库返工）

- **坑**：解析里写「官方**唯一**／明确**只有**这三类／官方**从不**…」这类替官方下的全称结论。它们读起来最像"考据充分"，实际最容易被官方原句直接打脸。
- **症状**：一轮全库复核（376 题）抓出 6 处这类实质错误，且**同一句错误论断在多个批次重复出现**——「官方在 ANR 语境下唯一点名的协程写法是 `Mutex.withLock`」在 batch-0003 出现 1 次、batch-0016 出现 2 次；接手时的交接文档只点名了其中 2 处。这些题机械层 26/26 全绿、`batch-check` 一条都不报（都是"语义层"错误）。
- **根因**：① 把「我检索到的」写成「官方只有」；② 只查了所引的那一页，没查同一站点**其它相关页是否给出不同阈值**——实测 Android 官方 `topic/performance/vitals/anr` 写「前台有 activity 时广播超时 5 秒」，而 `topic/performance/anrs/diagnose-and-fix-anrs` 的表格写「前台优先 intent 10／10–20 秒、后台 60／60–120 秒」，两页口径并不一致；③ 引号里的引文没逐字回原文核（本轮有一处引号句在所引页面与其 4 个相邻官方页**全部 0 命中**）。
- **规避**：
  1. 解析只写**题目断言范围内**的结论；要写「唯一／只有／从不／都」，必须能贴出官方原句并说明检索范围；
  2. 引号引文一律逐字回原文核，顺带核「这句话属于这一节吗」——本轮另抓出一处章节号错位（常量表达式是 JLS **§15.29**，解析写成 §15.28）；
  3. 这一模式可用 `python tools/bank-sweep.py` 全库粗筛（强断言词 AND 来源归属词），本轮把复查范围从 67 处收敛到 10 处；
  4. 粗筛命中**不等于错**（本轮有一处是「完整类名 vs 裸类名」的误报），必须逐条回官方页判。

## 二、App 域

### 2.1 Scaffold `containerColor=Transparent` 断开内容色链（1149bb5）

- **坑**：深色模式下页面裸 `Text`（section 标题）全变黑字，深色背景上看不见。
- **症状**：Read 截图缩略图看不出问题，需**像素采样**（脚本取 glyph 色值）才能定位。
- **根因**：`contentColorFor(Transparent)` 返回 Unspecified，`LocalContentColor` 链断裂回落默认黑色。
- **规避**：`Scaffold` 设透明背景时必须显式补 `contentColor = contentColorFor(...)`；排查黑字类问题用像素采样而非肉眼截图。

### 2.2 NavHost 的 saveState/restoreState 只保 rememberSaveable 与 ViewModel

- **坑**：以为切 tab 状态会自动恢复，普通 `remember` 状态实际即丢。
- **症状**：切 tab 回来列表/选中态消失，交接描述与实际行为不符。
- **根因**：状态持有方式（`remember` vs `rememberSaveable`）决定恢复行为，与导航参数无关。
- **规避**：需要跨 tab 保留的 UI 状态用 `rememberSaveable`（Set 需 List 桥接 Saver）；交接描述行为前先核实状态持有方式。

### 2.3 M3 ModalBottomSheet API 收紧（compose-material3 1.5.0-alpha+）

- **坑**：按旧 API 写 `rememberModalBottomSheetState(initialValue=...)`、调 `sheetState.animateTo()`、引 `SheetDefaults` 全部编译失败；`animateTo` 已 internal。
- **症状**：升级依赖后一系列编译错误链。
- **根因**：alpha 版本 API 快速收敛，公开面收缩。
- **规避**：目标档位用 `LaunchedEffect { sheetState.expand() / partialExpand() }`；不确定某 API 是否公开时，**解包 aar 查字节码**（python zipfile）而不是猜。

### 2.4 构建成功 ≠ 真机在跑新代码

- **坑**：构建成功后忘了 `adb install`，真机验证测到的全是旧行为（「功能失效？」）。
- **症状**：新功能在真机上不存在，日志/断点却显示代码「应该」生效。
- **根因**：把「编译通过」当成了「已部署」。
- **规避**：真机验证前固定动作 `adb install -r <apk>`；验证前截图确认前台界面符合预期。

### 2.5 真机自动化前确认手机空闲，验证完立即息屏

- **坑**：自动化点击闯进维护者正在使用的手机（他可能正在刷题）；或验证完屏幕常亮烧 OLED。
- **症状**：用户正在用的界面被自动化点击干扰；屏幕长时间点亮。
- **根因**：默认设备闲置，未验证前台。
- **规避**：自动化前后 `dumpsys activity activities | grep topResumedActivity` 确认前台是预期界面；结束时 `adb shell input keyevent 26` 息屏。

### 2.6 不可滚动容器内并列无高度约束的 LazyColumn，整页滑不动

- **坑**：批次管理页把「目录文件」和「已处理批次」两个 `LazyColumn` 直接放进一个普通 `Column`，都不给 `weight`/固定高度。
- **症状**：条目少时正常，批次增多后底部永远到不了，页面看似「卡死不能滑」。
- **根因**：`LazyColumn` 在无界高度约束里按内容测量，两个懒列表都不产生滚动，外层 `Column` 又不可滚。
- **规避**：同方向只保留一个滚动容器——多分区页面用**单个 `LazyColumn` + section header/items**；确需分区独立滚时才给内层 `weight(1f)` 限定高度。

### 2.7 Backdrop 液态玻璃：两个必踩的坑（ADR-0010）

- **坑 A（文档超前于发布版）**：官方 GitBook 的 `Interactive Glass Bottom Bar` 示例写 `shape = { ContinuousCapsule }`，但 **`backdrop` 2.0.1 与 `shapes` 1.2.1 里都没有这个符号**（三重验证：两个 `-sources.jar` 逐文件搜索 + Shapes 仓库文件树）。照抄文档 → 编译不过。
- **症状 A**：`Unresolved reference 'ContinuousCapsule'`；或用了自定义 `Path`/`GenericShape` 后运行期抛 `UnsupportedOperationException("Only RoundedRectangularShape or CornerBasedShape is supported in lens effects.")`。
- **根因 A**：文档站跟随 `kmp` 开发分支，不锁定发布 tag；`lens` 只接受 `CornerBasedShape` / `RoundedRectangularShape`，自定义路径用不了折射。
- **规避 A**：胶囊用 `com.kyant.shapes.Capsule()`（其 `style` 默认已是连续曲率）；要新 API 先解包对应版本的 `-sources.jar` 核实存在性，别信文档代码。

### 2.8 依赖只声明 backdrop 时用不了 Capsule（implementation 不透传编译期）

- **坑**：`backdrop` 对 `io.github.kyant0:shapes` 是 `implementation`，**不在编译期类路径上**；只声明 backdrop 时用 `Capsule()` 会解析不到。
- **症状**：`Unresolved reference 'Capsule'`——尽管运行时类一定存在（backdrop 会把它带进来），编译期就是看不见。
- **根因**：Gradle 的 `implementation` 不向消费者传递编译期类路径（`api` 才传递）。
- **规避**：显式声明 `implementation(libs.shapes)`，且**版本与 backdrop 内部依赖保持一致**（现为 1.2.1），避免同一库出现两个版本。

### 2.9 玻璃效果在 native 层崩溃，Kotlin 层 catch 不住

- **坑**：`backdrop` 的 FAQ 记录过玻璃叠玻璃时的 `Fatal signal 11 (SIGSEGV) ... RenderThread`。想「自动检测并降级」到无玻璃模式。
- **症状**：App 直接闪退，logcat 只有 tombstone，没有任何 Kotlin 异常栈可捕获。
- **根因**：崩溃发生在渲染线程的 native 代码里，Java/Kotlin 的 `try/catch` 与 `Thread.setDefaultUncaughtExceptionHandler` 都拦不到。
- **规避**：**放弃自动兜底**，改为如实记录风险（ADR-0010）。崩溃时切回「标准」即可恢复——设置存 DataStore、不依赖渲染链路，故 App 起不来时改设置也有效。避免玻璃叠玻璃（不要嵌套 `layerBackdrop`，需要多层时用 `exportedBackdrop`）。

### 2.10 速度驱动的拉伸必须取绝对值（否则反向拖会变成收缩）

- **坑**：胶囊按拖拽速度做液滴拉伸时，直接拿带符号的速度算 `1f + v * k`。
- **症状**：往右拖时胶囊横向拉长（对），往左拖时却横向**收缩**（错）——观感像被压扁而不是被甩出去。不崩不报错，只有肉眼能看出，容易当成「设计就是这样」蒙混过去。
- **根因**：拉长是**沿运动方向**的形变，与运动的正负方向无关；带符号速度把「往哪边」也编码进了幅度。
- **规避**：对速度取绝对值 `abs(v)`，横向拉长、纵向补偿收窄。这类「算错不崩、只错手感」的纯计算**必须抽成可测函数并锁住**（见 `BottomBarDragMathTest`）——本坑就是被单测抓出来的。

### 2.11 把视觉的全部维度都挂在「按压进度」上，松手后会退回半成品

- **坑**：胶囊的高光、内阴影、外投影、边缘色散、面层透明度全用「按压进度」`progress` 驱动（`alpha = progress`、`lens(px * progress)`），`progress` 又只由手指是否按着决定。
- **症状**：按住时是一块漂亮玻璃，**松手立刻退回一块静态淡色块**（高光内阴影全没了）。若另一个状态（如拖动中）恰好一直按着，还会造成「拖动时好看、停下就变样」的错觉，像 bug 但不是。
- **根因**：把**状态外观**（选中项应该是玻璃）与**受力反馈**（按下去鼓起来）混在同一个变量上。按压力度天然是瞬时的，用它承载持久外观必然在松手时归零。
- **规避**：把两者拆开——**外观常驻**（高光/内阴影/投影/色散始终在），`progress` 只负责**瞬时的加强**（缩放、折射增量）。判断标准：问一句「这个量在手指离开后该不该还在？」，答「该」就不能挂在按压进度上。

### 2.12 玻璃材质「只有选中项漂亮」——高级效果只加在了胶囊上，没加到底栏本体

- **坑**：给 `drawBackdrop` 的选中胶囊配齐了高级材质（`chromaticAberration` 色散 + `Highlight` 高光 + `Shadow` 外投影 + `InnerShadow` 内缘压暗），却把**底栏本体**（`barMaterial`）只写成 `vibrancy() + blur() + lens()`——没有色散、没有高光。
- **症状**：**按住选中项（或拖到该项）时是一块完整的高级玻璃，一松手/停在别的 tab 就「挺普通」**。维护者原话：「色散效果、膨胀效果只有从『练习』Tab 长按或滑动才有完整的高透、色散等高级材质效果，其他 Tab 滑动就挺普通的」。不崩不报错，极易被误判为「背景内容不同」或「采样位置错」。
- **根因**：底栏与胶囊是**两层独立材质**，两处配方不对称。底栏是四个 tab **常驻**的那一层；胶囊只在选中项处。只给胶囊加料，观感就变成「选中项特殊、其余普通」，而用户真正的诉求是**整条底栏在任何 tab 下都是同一套材质语言**。
- **规避**：**底栏本体与选中胶囊共用同一套配方**（`chromaticAberration` + `Highlight` + `Shadow` + `InnerShadow` 一个不能少），差异只允许出现在**尺度**上（底栏内缘压暗半径比胶囊收敛）。新增一个高级效果时，先问「底栏本体有没有？」
- **测试性说明**：本坑**没有 JVM 单测 seam**（依赖真机 backdrop 渲染链路）。但它的排查不该靠反复截屏——**先做两处材质的配方对照**（把 `barMaterial` 与 `CapsuleIndicator` 的 `effects`/`highlight`/`shadow`/`innerShadow` 逐项列表对比）通常一眼就能定位，成本远低于像素测量。
- **排查教训（重要）**：本坑最初被误判为「`graphicsLayer.translationX` 导致 backdrop 采错位置」，绕了很远。两次独立测量均证伪该假设：轴向 A/B（`offset` vs `graphicsLayer.translationX`）四槽位像素差 **+0.00**；通道互相关在四槽位峰值偏移均为 **0**（无通道错位）。**教训一：先做「配方/参数对照」这类静态代码比对，再考虑上像素测量。教训二：上像素测量前必须先自证测量协议有效，见 3.6。**

### 2.13 异步数据分批到达时，别让"先到的 section"占据首帧顶部（批次导入闪烁）

- **坑**：批次导入页同时等两路数据——SAF 目录扫描（慢）与 Room 已处理批次流（快）。目录区用 `if (batches.isNotEmpty())` 门控，已处理区无条件渲染；首帧/转场期间目录为空，**已处理列表先上屏并占住顶部**，SAF 返回后整个目录区（标题+按钮+10 张卡）再「插入」到它上方。
- **症状**：进入页面的转场动画（300ms）中有几帧画面顶部是「已处理批次」，随后内容整体下跳、目录区出现在顶部——用户感知为**闪烁/跳一下**。静态截图（进入后 2 秒拍）永远抓不到，必须录屏逐帧看（`screenrecord` + ffmpeg 抽帧）。
- **根因**：单个 LazyColumn 里多个数据到达时机不同的 section，只对慢数据做了空态门控，却让快数据在慢数据就绪前先占位；Compose 重组插入新 item 时保持滚动锚点，视觉上就是「后到的内容把先到的顶下去」。
- **规避**：用一个**首帧门控状态**（如 `initialized`）——首次慢数据就绪前，除固定操作行与 loading 外的所有 section（含快数据 section）一律不渲染；慢数据骨架一到解除门控，完整列表一次性出现。已初始化后的 ON_RESUME 重扫静默进行（不回退门控）。原则：**同一屏的异步 section 要么一起出现，要么显式给整页 loading，不要让它们分批插入布局。** 现已收口为可复用模块：`ui/components/Loadable.kt` 的 `collectAsLoadable`（值到达后不因重订阅回落首帧态——那正是 2.16 的成环陷阱）。

### 2.14 「列表为空」兼作加载中/空结果/参数丢失，转圈永不结束

- **坑**：会话页用 `questions.isEmpty()` 一个条件同时表示「还在查」「查完是空的」「参数根本没传到」，三种成因一律渲染 `CircularProgressIndicator` 后 `return`。
- **症状**：点「开始练习」后会话页转圈不停，没有错误、没有返回入口，用户只能杀 App；日志干净（协程正常结束，只是再没有任何分支会把列表写满）。真实触发路径是**重复压栈**：第二层会话的 `previousBackStackEntry` 是上一层会话而非配置页，参数读不到。
- **根因**：把异步的三种成因塌进一个布尔式判断；`if (list.isEmpty()) { 转圈; return }` 里缺「已完成且为空」这一支，于是「空」永远等价于「还在加载」。
- **规避**：异步结果用**具名四态**（Loading / Ready / Empty / Failed）承载，转圈只可能来自 Loading，其余各态都必须给出路（返回，或在可重试时给重试）；成因用有限枚举而非自由字符串，文案走 `stringResource`、行为可单测。落地见 `data/practice/SessionLoad` 与 `PracticeSessionLoader`。首帧门控（2.13）与本条同族，一起看。

### 2.15 会话状态裸 remember + 已落库的副作用 = 配置变更清空却污染统计

- **坑**：作答、已提交结果、跳过标记、在途提交全用裸 `remember`（无 `rememberSaveable`、无 ViewModel）持有，而提交动作**已经把记录写进 Room**。
- **症状**：切系统深色模式（含夜间自动深色）、改字体或显示大小后，会话回到第 1 题、进度全空；用户重做同一题会落下第二条记录——「全部作答正确率 / 平均得分率 / 作答次数」同题算两遍，`consecutive_perfect` 被多推一次（错题被加速消解）。**「首次作答正确率」看不出问题**（首答记录已写定、重建后的记录不进该指标），只盯它会误判为无事。
- **根因**：`remember` 只活到组合销毁，Activity 重建即丢；但副作用已落在持久层，两者不同步。本项目 Manifest 未声明 `configChanges`，所以任何一项配置变化都会重建 Activity。
- **规避**：会话状态放 **NavBackStackEntry 作用域的 ViewModel**——配置变更时它随 Activity 的 ViewModelStore 存活，进程终止才消失，正好就是需要的边界。进程终止的判定用**进程级令牌 + 参数比对**（`data/practice/ProcessToken`，必须是 `object` 单例：挂在 Activity 级容器上会随重建换值，把配置变更误判成进程终止）；不要用 `savedInstanceState != null`（两种重建都为真）、不要用 entry id（恢复时复用）。另外 `rememberPagerState` 内部走 `rememberSaveable`，所以它会**跨重建恢复当前页**——状态存活方式不一致会让问题更隐蔽。

### 2.16 在组合里现造 Flow 会自持成环，整页疯狂闪烁

- **坑**：`container.xxx.observeYyy().collectAsStateWithLifecycle(initialValue = …)` —— 每次重组都新建一个 Flow 实例，而这个 API 以 flow 为 key，于是**每次重组都重订阅一次**。若「首帧态」绑在「这次收集刚开始」上（如 `onStart { emit(FirstLoad) }`），重订阅就会把门控重新关上：数据到达 → 触发重组 → 组合里又现造一个新 Flow → 重订阅 → 重发首帧态 → 整页内容消失 → 再取数据 → 再重组……**自持成环**。
- **症状**：切到该 tab 后内容区**整块**空白一两秒才出现，之后每次状态变化（点筛选 chip、滚动）再闪一次。日志干干净净（无异常、协程正常结束），截图也看不出规律——很容易被当成「渲染慢」或「Room 慢」。
- **根因**：把「**还从没**拿到过值」（一次性事实）与「**这次**收集刚开始」（每次订阅都发生）混为一谈。
- **规避**：① 流来源用 `remember` 持有稳定实例；② 门控状态**只写不回退**——拿到值之后即使重订阅也不回落首帧态。本项目收口在 `ui/components/Loadable.kt`：`LoadableState.collectFrom` 只写 `Data`，并因此留下了单测缝（连收集两次，断言不回落）。**通用判据**：任何「首次态 / 加载态」都只能由「还没拿到值」驱动，不能由「订阅开始」驱动。

### 2.17 底栏的 ime 分支是防御性代码，藏着「tab 屏永无输入框」的假设

- **坑**：`ZhilianBottomBar` 内部避让写的是 `windowInsetsPadding(navigationBars ∪ ime)`，但四个 tab 屏都没有文本输入——这个 `ime` 分支**今天恒为 0**，属防御性代码；它成立的隐含前提是「tab 屏永远不会出现输入框」，而这条前提没写在任何地方。
- **症状**：前提一旦破裂（某个 tab 屏加了搜索框），底栏会被键盘顶到键盘上沿，而该屏的底部留白（由 tab 屏外壳 `TabVerticalScrollColumn` / `TabLazyColumn` 叠加）**只算底栏高度 + 手势条、不含 ime**——最后一项正好压进「键盘 + 底栏」那一块，且只有真机弹起键盘再滚到底才看得见。
- **根因**：底部空间有**两个计算者**，各自用的 inset 集合不一致——底栏自己算 `navigationBars ∪ ime`，屏内容只算 `navigationBars`。二者今天数值互不冲突（因为 tab 屏无输入），所以看不出问题。
- **规避**：给 tab 屏加输入框时**必须两处一起改**——① 该屏底部留白叠加 ime（或改用 `Modifier.imePadding()`）；② 复看底栏被顶起后是否仍符合 ADR-0010 的穿透模型。只改一处会留下「最后一项被遮且在真机才复现」的静默回归。

### 2.18 MuMu 的软键盘不占屏，ime 相关行为在模拟器上验不了（假阴性陷阱）

- **坑**：在 MuMu 上用 uiautomator / dumpsys 验「键盘弹起后输入框会不会被遮」——`dumpsys input_method` 明明报 `mInputShown=true mImeWindowVis=3`，看着键盘已经弹出；但 `dumpsys window windows` 里输入法窗口是 `frame=[0,1920][1080,1920]`，**高度为 0**——软键盘根本不占屏。
- **症状**：`Modifier.imePadding()` 在该环境下永远加 0，键盘弹出前后所有控件坐标**一模一样**。据此得出「键盘避让没问题」是**假阴性**；真机可能完全不是这样（真机有真实键盘高度，才会暴露双重位移、遮住提交按钮等问题）。
- **判据**（在模拟器上想验 ime 前先自检）：`adb shell dumpsys window windows` 找到 `Window #.*InputMethod` 块，看它的 `Frames: … frame=[x1,y1][x2,y2]`；`y2 - y1 == 0` 就说明这台设备验不了 ime，别浪费时间。
- **规避**：键盘 / ime 相关行为**一律真机验**（属 AGENTS.md 红线 3 里「模拟器复现不了」的情形）。模拟器上能验的只是「键盘没弹时布局对不对」。

### 2.19 电脑端改了批次，手机端「照样进不来」——三道闸门 + 导入顺序造成的停用丢失（2026-10-05）

- **坑**：期望「电脑端改 JSON → Syncthing 同步 → 手机自动拿到更新」，实际手机端一动不动。旧模型的**三道闸门**各自独立、任一处都拦住：① 按 `batchId` 判「已处理」就不给导入按钮；② 按 `questionId` 判「已存在则跳过」；③ `batchOrder` 冲突整批拒绝。且 `questions` 只追加、不原位改内容。
- **症状**：改了题干/答案/分类，手机端刷到的还是旧内容；连续两次「清库重导」才能看到。更隐蔽的一次：用户直接点「全部导入」，`batch-0018` 早于 `batch-0011` 入库——0018 的 `retiredQuestionIds` 指 0011 的新题，导入 0018 时该题还没入库，停用被记成「不在库」提示后**静默丢失**；随后 0011 入库又把它建成可用题，题库多出一道本应停用的题。
- **根因**：把「批次文件」当成一次性交付、把「已处理」理解成「永不再看」；停用与写题在同一批内耦合，导致跨批次停用依赖批次导入顺序。
- **规避**：改为**目录为权威源的题库对账**（ADR-0017）——① 用**内容指纹**（`processed_batches.content_hash`）判「已对账」，内容变了才算待对账；② 同 `questionId` **原位覆盖内容列**（保留 `inactive`/掌握度/收藏/`imported_at`）；③ **两阶段**：单事务内先写所有批次的题，再统一执行全部变化批次的 `retiredQuestionIds`——顺序依赖结构性消失。**别再回到「点导入才更新」的老路**，也别把「只增不删」误当 bug（删除只走手动「撤销批次导入」）。

### 2.20 对 `asRead()` 包装的设置流用 `first()`，会拿到 `Read.Pending` 导致逻辑永远空转（2026-10-05）

- **坑**：前台自动对账要读「批次目录」设置，写成 `settings.batchTreeUri.first().valueOrNull`，判空后直接返回。看着没问题，实际每次都对空跑。
- **症状**：功能「静默不工作」——对账从不落任何写入、摘要永不出现、目录扫描（用 `collectAsStateWithLifecycle` 连续收集）却一切正常。**两边读同一个流，一边有值一边没有**，极易误判成「SAF 权限问题」或「文件读不到」。代码里连日志都看不到（日志写在判空之后）。
- **根因**：`Read<T>` 流由 `asRead()` 产出，它 `onStart { emit(Read.Pending) }`——**首个发射恒为 Pending**（因为设置读盘是异步的）。`first()` 取的就是这第一个值，`valueOrNull` 恒为 null。
- **规避**：取「第一个真正的值」用 `first { it !is Read.Pending }`（再 `valueOrNull`）；别对 `Read` 流用裸 `first()`。UI 侧连续收集不受影响（它会等到 `Read.Value`）。**通用判据**：凡是「首帧可能是 Pending」的流，`first()` 与 `collect` 的语义不同——前者会停在 Pending，后者会继续。

### 2.21 「指纹一致整批跳过」把停用声明一并跳过——撤销重导后本应停用的题回到可用态（2026-10-05）

- **坑**：`BatchReconcilePlanner` 把「批次指纹一致」实现成了「该批一切声明都不参与本轮」。停用声明写在 A 批、题目属于 B 批时：B 被「撤销批次导入」删掉（连带删它的已处理记录 → 下轮变待对账），题目被重插，而 A 指纹未变被跳过 → A 的 `retiredQuestionIds` 再不重放，那道题**永久停在可用态**。
- **症状**：库里多出一道本应停用的题，**无任何报错或待处理提示**——`retiredMissing` 只统计变化批次，连「缺失提示」都不留。与 ADR-0017 开篇声称已「结构性根治」的 batch-0018 事故同形，只是触发门从「导入顺序」换成了「撤销后重导」。
- **根因**：把「内容无需写入」当成「该批无副作用」。停用的正确语义是**目录级不变量的每轮重放**，不是「只在批次变化时执行一次的动作」。
- **规避**：停用并集取**目录级**（变化 + 未变批次），并把目标限制为「本轮写入后处于可用态」——已停用的不重复计入，`markInactive` 因此是幂等空转，摘要的 `retired` 也等于真正新停用的题数（否则每次开 App 都留一条「停用 1」的噪音摘要）。被 blocked 批次不参与重放。**通用判据**：任何「按指纹/哈希跳过整块处理」的优化，都要问一句——这块除了数据本身，还声明了什么副作用？

### 2.22 测试替身把「只更新部分列」建模成「整行替换」，让核心声明在测试里是反义（2026-10-05）

- **坑**：`BatchReconcileServiceTest.FakeReconcileStore.updateQuestions` 直接 `questions[i] = updated`，等价于 Room 的 `@Update`；而真实 DAO 是 `updateContent` 逐列点名、保留 `inactive` / `consecutivePerfect` / `hasEverWrong` / `favorite` / `importedAt`。
- **症状**：ADR-0017 最关键的承诺「同 ID 原位更新但作答历史与掌握度保留」在编排层测试里**没有任何断言守着**——要哪一天真实 SQL 被改回整行 `@Update`，全套测试照样绿。
- **根因**：替身按「最省事」写，没和它所替代的那条 SQL 逐列对齐；测试看起来在验业务规则，其实在验替身自己的假设。
- **规避**：替身必须复刻**被替代实现的行为契约**而不是它的意图——现按 `updateContent` 同口径 `updated.copy(保留五列)`，并由 `同 ID 更新不清本地状态` 断言守住。同理 `markInactive` 现在会把题置 `inactive = true`，否则下一轮对账看不出「已是停用态」（见 2.21）。

## 三、工具与流程域

### 3.1 git add 夹带越权改动（28ffc0b 事故）

- **坑**：出题代理越权直改规范文件，被维护者的 `git add` 无意夹带进一次合规提交。
- **症状**：提交后 diff 里混着与提交主题无关的文件改动。
- **根因**：用了宽泛 `git add` 且没审查 staged diff。
- **规避**：**git add 前必须审查完整 staged diff**；只精确 add 任务相关文件（禁 `git add -A` / `git add .`）。

### 3.2 工具回执可能污染，投放类操作必须分步重验

- **坑**：命令回执里混入未请求的输出、文件大小张冠李戴、并发会话的写入痕迹——直接相信回执会在不可逆操作上做出误判。
- **症状**：回执显示「成功」但细节自相矛盾（如复制回执里出现没写的 hash 命令）。
- **根因**：回执文本只是参考，不是事实本身。
- **规避**：投放/删除等不可逆操作固定三步：`Test-Path`（存在性）→ 列目录（真实状态）→ 两侧 `Get-FileHash` 交叉核对，全部吻合才宣布完成。

### 3.3 中文路径构建报错

- **坑**：项目路径含中文时 Gradle 构建失败。
- **症状**：路径检查错误直接终止构建。
- **根因**：AGP 默认拒绝非 ASCII 路径。
- **规避**：`gradle.properties` 中 `android.overridePathCheck=true`（本仓已配置；新工程首次构建报路径错误时先查这条）。

### 3.4 二手汇总数字引用前先跑磁盘统计（「75→90」实有 87 题）

- **坑**：交接文档写「batch-0008 导入后 75→90」，维护者未核就转述给用户；磁盘逐批统计实际是 87（0008 是 12 题不是 15）。
- **症状**：用户按 App 实际题数反问「为什么只有 87」，预期数字被证伪。
- **根因**：把交接文档/他人汇报里的派生数字当事实——它和工具回执一样只是「显示层」。
- **规避**：向用户报告题数、字节数、比例等派生数字前，先从磁盘现算（批次题数直接解析 JSON 统计）；引用交接文档时只信可复现的一手标识（文件路径、hash、命令），不信口算结论。

### 3.5 引用文件路径要验到目录，不能只验文件名存在（batch-0010 任务书）

- **坑**：写任务书时用 `Get-ChildItem -Recurse -Filter 文件名` 确认 8 篇笔记存在，但在任务书里手写归属目录时把 6 篇全安到了不存在的 `03-多线程/`（实际在 `05-常用接口/`、`06-并发编程/`）。
- **症状**：文件名查询全部命中，让人以为"路径也核实过了"；代理拿到错误路径可能误判"笔记缺失"。
- **根因**：把「文件存在」这一**部分事实**当成「路径正确」的**完整事实**——`-Recurse -Filter` 只验了叶子名，没验父目录，输出里的 `FullName` 才是完整路径却没采用。与 3.4「部分核实当成完全核实」同型。
- **规避**：任务书/文档里写具体文件路径时，直接用磁盘命令输出的 `FullName`（或相对根的完整相对路径），不靠文件名 + 记忆拼父目录；引用前把"名"和"路径"当两个独立事实分别验。

### 3.6 adb 自动化点击坐标以 uiautomator dump 的真实 bounds 为准，勿按截图目测

- **坑**：按 `screencap` 拉出的截图目测坐标 `input tap`，连续点空（点到邻接控件，如想点「开始练习」却反复弹题量面板）。
- **症状**：tap 回执成功但界面无反应或触发错误控件。
- **根因**：截图经 pull/查看后分辨率被缩放显示（本机物理 1280×2772，截图目测按 ~1080 宽换算），坐标系对不上。
- **规避**：关键点击先 `adb shell uiautomator dump /sdcard/ui.xml` 取目标节点 `bounds="[x1,y1][x2,y2]"`，按真实中心点 tap；先 `wm size` 确认物理分辨率。截图只用于判读界面状态，不用于量坐标。

### 3.7 像素测量前必须先自证「测量协议」有效（`input motionevent` 的 slop 陷阱）

- **坑**：用 `adb shell input motionevent DOWN/MOVE/UP` 分步驱动 Compose 手势做逐槽位截图，**默认「MOVE 到哪，界面就在哪」**。
- **症状**：同一份数据反复得出互相矛盾的结论——某槽位测出「效果 = 0.00（完全无效）」，换次采集又变成「四个槽位都有」。据此先后推翻过两个根因假设，都是假的。
- **根因**：`awaitTouchSlopOrCancellation` 把 `startX` 设在**跨过触摸阈值的那一次 MOVE** 上。故 `DOWN → MOVE(小幅)` 只用来「起拖、建立 startX」，**本身不产生任何位移**。若直接按「目标槽位」发 MOVE，胶囊实际停在**前一格**，截图与槽位标签整体错位；更糟的是两次不同意图的采集可能让胶囊落在**同一位置**（两帧逐字节相同，MD5 一致），于是差分恒为 0，被误读成「这里没有效果」。
- **规避**：
  1. **先自证协议**：发完一组事件后，先核对**各帧 MD5 是否互不相同**——出现重复即协议无效，任何差分结论作废；
  2. **显式 priming**：先 `MOVE` 一个明确跨过 slop 的量（本项目底栏 slop = 12dp，1080p/480dpi 下约 36px），再按**整倍槽宽**移动，使落点精确落在整数序号上（如槽宽 246px：`MOVE 220` 起拖，再 `MOVE 466 / 712 / 958` → 序号恰为 0/1/2/3）；
  3. **用自参照差分而非启发式**：判定「某处有没有效果」，拿**该处有覆盖物的帧**与**该处无覆盖物的帧**相减（同一区域、同一页面内容），不要靠「暖色像素」「色差阈值」这类启发式——本轮暖色启发式一度给出完全相反的结论（1508/1533 个暖色像素落在胶囊并不在的那一格）。
  4. 结论与代码不符时，**优先怀疑测量而非代码**；先回去做静态代码比对（见 2.12）。

### 3.8 `uiautomator dump` 失败时 `pull` 会拉回上一份陈旧 XML，把界面判成旧状态

- **坑**：用 `adb shell uiautomator dump /sdcard/ui.xml` + `adb pull` 循环读界面，隐含假设「拉到文件 = 读到了当前界面」。
- **症状**：同一串操作得出互相矛盾的判断——按了返回键「还停在会话页」、点过的控件「没生效」、页面「毫无变化」；没有任何报错，因为 `pull` 是成功的。本轮据此一度误判「返回键不 pop」。
- **根因**：`uiautomator dump` 在动画/转场/首帧期间会失败（`ERROR: could not get idle state`），而 `/sdcard/ui.xml` 仍是**上一次**的旧文件，`pull` 照样成功——拿到一份看起来完全正常的陈旧快照。dump 失败与 pull 成功之间没有校验点，两者又共用固定路径。
- **规避**：三步固定动作——① dump 前 `rm -f` 远端文件（**缺文件比旧文件安全**：pull 会失败而不是静默给旧数据）；② 校验 dump 回执含 `dumped to`，不含则重试（间隔数百毫秒，最多几次）；③ 重试仍失败就当「读不到」，**不要**把陈旧快照当成「界面没变」的证据。与 3.7 同族：先自证测量协议有效，再相信测量结果。
- **附带一条**：`uiautomator dump` 只包含**可见**节点——折叠线以下的元素根本不在 XML 里。判断「某控件有没有渲染出来」之前，先确认它在视口内（或先滚动到它），否则会把「在屏幕外」误判成「没渲染」。切换 tab / 页面后还要**轮询等待目标文本出现**再断言，转场期间 dump 到的是上一页。

### 3.9 PowerShell「路径带通配符 + `-Recurse` + `-Filter`」会从**父目录**递归，造出假的参照集（2026-10-05）

- **坑**：把「单层收集批次 JSON」写成 `Get-ChildItem "D:\...\batch-*" -Recurse -Filter "batch-00*.json"`，以为通配符 `batch-*` 把范围限制在那几个子目录里。
- **症状**：本应 8 个参照批次，实际扫出 **16** 条——多出的 8 条来自 `_staging\`，而它**同时又是拷贝目标**（自己拷自己）。核对工具照常打印「通过」，肉眼看不出异常；真正的危险是参照集里会混进**任何**躺在父目录下的旧副本，拿陈旧文件比对就是假绿灯。这条命令还曾被同步写进两份 README 与两份统筹 prompt，等于把坑分发了四份。
- **根因**：`-Path` 的通配符与 `-Recurse` 组合时，枚举**不是**「先按通配符筛出目录、再在目录内递归」，而是从通配符所在层级的**父目录**起递归再套 `-Filter`。旁证：同一条命令**去掉 `-Recurse` 返回 0 条**——`-Filter` 在通配符展开阶段就被消费掉了，两层机制互相干扰。
- **规避**：**不要在带通配符的路径上用 `-Recurse`**。拆成显式两步——先 `Get-ChildItem <root> -Directory | Where-Object { $_.Name -match '^batch-00\d\d$' }` 精确挑目录，再对每个目录 `Get-ChildItem -LiteralPath <该目录> -File -Filter ...` 取文件；并在拷贝后**加硬闸**断言「暂存数 == 源数」，不等就 `throw`。**「发现了 N 个」不构成验证，必须断言 N 等于预期值。**

### 3.10 PowerShell 的 `@($null).Count` 是 **1** 不是 0——用它判「字段缺失/为空」会得出反向结论（2026-10-05）

- **坑**：用 `@($_.answer).Count -eq 0` 判断 JSON 里某字段是否为空或缺失。
- **症状**：8 个批次共 16 道填空题的 `answer` 字段**实际全部缺失**，脚本却报告「answer 为空 **0** 题」——结论正好反了，据此差点把一个不存在的缺陷写进结论（幸好与另一处直读输出矛盾，才追出根因）。
- **根因**：`@($null)` 把 `$null` 当作**一个元素**包进数组，`.Count` 得 1。并且「属性不存在」「属性为 `$null`」「属性是空数组」这三种情况在该写法下**无法区分**。
- **规避**：分两步——先用 `$q.PSObject.Properties['answer']` 取属性对象（得到 `$null` 即字段缺失），再对它的 `.Value` 判空数组；或干脆用 Python 读 JSON（`json.load` 的语义没有这层歧义，本轮改用 Python 后立刻得到正确结果）。**通用原则：判空之前先验证判空函数本身。**

### 3.11 `git commit` 的 `-F` / `-m` 写在 `--` 之后会被当成路径（2026-10-05）

- **坑**：为「只提交指定文件」而写成 `git commit --only -- <paths> -F msg.txt`。
- **症状**：报 `fatal: ... is outside repository`，看起来像路径写错，实际是**参数顺序**错——`-F` 与消息文件都被当作 pathspec 解析。
- **根因**：`--` 之后的一切**一律按路径解释**（这正是 `--` 的定义），选项必须全部写在它前面。
- **规避**：`git commit --only -F msg.txt -- <paths>`——**所有选项在前，`--` 紧贴路径列表**。长中文提交信息走 `-F` 消息文件（避开 shell 引号与编码问题），但 `-F` 同样必须在 `--` 之前。
- **再附带一条**：用「连续截图哈希是否变化」判「页面在不在闪」会被**状态栏的分钟时钟**污染——跨过整分钟那一格，任何静止页面也会给出两种哈希（本轮据此误判过一次：修复后「练习」页反而出现两种帧，而真正的问题页变得稳定）。闪烁类判据改用**语义信号**（如「采样界面文本数是否抖动」），或先裁掉状态栏再比哈希。
- **还一条**：布局判据会因布局本身变化而失效，改完要**重新定义判据**再自证。本轮判「练习页有没有露出相邻卡片」，第一版用「屏幕最右 8dp 内有没有卡片色像素」，卡片改成通栏后**它自己就顶在屏缘**，同一判据立刻给出假阳性；正确特征是「卡片与屏幕缘之间有没有一条背景带」。

### 3.12 PowerShell 的 `-notmatch` 用在数组上返回「不匹配的元素」而不是布尔（2026-10-05）

- **坑**：批量验证写成 `if ($out -notmatch "结论：通过") { 报 FAIL }`，而 `$out` 是命令输出按行拆成的**数组**。
- **症状**：24 个批次明明全部通过，脚本却报 **24/24 全 FAIL**；同型的 `-match` 写法反而正常——一度让我以为整轮改写全废。
- **根因**：`-match` / `-notmatch` 作用在数组上是**逐元素匹配并返回匹配（/不匹配）到的元素集合**——`$out -notmatch X` 只要有一行不含 X 就非空、即判为真，于是「任一行不含」被当成「校验失败」。与 3.10（`@($null).Count`）同属「运算符落到集合上语义与直觉相反」。
- **规避**：**先收敛成单值再判**——先把输出 `-join` 成一个字符串再 `.Contains("结论：通过")` 取反；或直接 `$out | Select-String -Quiet`。**通用原则同 3.10：先拿一个已知通过的样本验证判据本身，再上全量。**

### 3.13 清理类操作不能以删除工具回执为准，要用「ignore 规则 + 跟踪状态」双确认（2026-10-05）

- **坑**：调删除工具清 `app/build/` 下的一次性产物，工具**连续三次**回执 success，文件实测仍在（`Get-ChildItem` 照常列出、`Test-Path` 仍为 True）。
- **症状**：回执说删了，目录说没删——和 3.2 一样是「回执属于显示层」，但这次连重试都不能纠正，重试三次得到三份同样的假回执。
- **根因**：「文件被删掉」与「文件不可能进版本库」是**两个可独立验证的事实**；删除动作不可信时，后一个事实依然能被证明。把「删成功」当成「没有污染风险」的**唯一**依据，就会在一个可独立证否的结论上依赖一个已知会说谎的信道。
- **规避**：清理类操作分两层复核，缺一不可——
  1. **事实层**：删完**重列目录**，匹配数必须为 0，并断言它等于预期值（「发现了 N 个」不构成验证，见 3.9）；
  2. **风险层**：`git check-ignore -v <path>`（确认被哪条规则覆盖、规则行号）+ `git ls-files <path>`（返回空即未被跟踪）双确认，证明该文件不可能进入公开仓库。
  - 两层结论矛盾时（回执 success 但重列仍在），**以重列为准**，并在结论里写成「未真正删除，仅证明不入库」——不要因为回执好看就报「已清理」。该次处置即：如实报告「回执说删了、目录说还在」，说明 `gradlew clean` 会带走，交用户决定；用户同意后改用 shell `Remove-Item` 重删，并同样以「重列匹配数 = 0 + `check-ignore` + `ls-files` 为空」复验通过——**换工具重删也要重跑同一套复验，不能因为换了手段就默认它可信**。

### 3.14 跨行短语与锚点检索：负结果必须先自证协议（2026-10-05 章节号核查）

- **坑**：在落盘的官方页上做「有没有这句话／这个章节号」的检索，把 **0 命中**直接当成「官方没写」。
- **症状**：同一轮核查里，作者本人连续两次因协议错误得出假结论——① 搜 `If the app has any activity in the foreground` 命中 0，实际原文在 `any activity in the\nthe foreground` 处**换行**，句子真实存在；② 用 `^\s*8\.4\.8\.1\.` 在**未去标签**的 HTML 上查章节号，8 个编号全部「未命中」，改用 `id="jls-15.29"` 仍是 0 命中——**是拿已知存在的 §15.29 当阳性对照才发现的**；若不自证，就会把「题库章节号普遍写错」这个不存在的结论报出去。
- **根因**：JLS 的标题有**三种标记形态**（目录锚点 `<a href="…#jls-15.29">`、编号与标题隔着 `</a>`、纯文本 `>` 编号 `.` 标题），任何单一假设都会漏；而行内正则天然不跨行。**「查不到」与「不存在」之间隔着一层协议。**
- **规避**：
  1. **先自证协议**：拿**已知存在**的样本做阳性对照（必须命中）、拿**已知不存在**的样本做阴性对照（必须不命中），两者都通过才允许输出负结果；
  2. 跨行短语检索：先把文档空白折叠成单空格，或正则用 `\s+`；
  3. 章节号检索：用 `>\s*<编号>\.\s*(?:<[^>]+>\s*)*标题`，并兼容锚点形态；
  4. 工具化：`python tools/check-citations.py`——它的步骤 0 就是这两组对照，不通过就**拒绝输出任何结论**并返回退出码 2。**通用原则同 3.7／3.10：先验证判据本身，再上全量。**
