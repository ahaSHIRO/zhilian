# 题目篇幅硬约束，并用一次「全库重排」破例改写存量批次

> **表述修订（2026-10-05）**：本文多处（「追加式修订的代价不可接受」「清库重导的代价可接受」、代价段「重排后清库重导」「App 侧除清库重导外零改动」）建立在**「App 是追加式导入、改了 JSON 不会更新已入库题目」**这一前提上。该前提已被 [ADR-0017](./0017-directory-authoritative-reconciliation.md) **取代**——题库对账会按同一 `questionId` **原位更新**内容（历史保留）。因此**今后的全库重排不再需要清库重导**，同步到手机即自动生效；本文其余结论（篇幅硬线、为何破例改存量）不变。本次 `batch-0001~0026` 重排当时尚无对账功能，故确实走了清库重导。

「知练」的定位是**碎片时间刷题**——单题应当在等车、排队的间隙读完并作答完。首次体感测试（2026-10-05）暴露存量题库与此定位冲突：26 批 376 题里，题干字符数 p90 = 761、max = 3472；程序题（129 道）的最大代码块中位数就有 **16 行**、max = **104 行**；解析中位数 **922 字**、**97.9% 超过 300 字**。长题干 / 大段代码 / 长解析消耗精力，是刷题体验的主要痛点。

对此本决策为两件事：

1. **篇幅成为硬约束**（出题规范 §三）：题干（去代码后）**≤100 字**、单题代码块**≤1 个且 ≤6 行**、题干（含代码）**≤180 字**、解析 **≤400 字**；程序题占比由「<20%」收紧到 **≤10%**。由 `tools/batch-check.py` 机械拦截。
2. **存量全库一次性重排**：对 `batch-0001~0026` **原位重写**批次 JSON（保留 `batchId`/`batchOrder`/`questionId`，只改内容），把长题压短、长代码题降级为短概念题，并以**基础/关键知识点为主**（定义型题不再排除）。这**打破了「首版只追加」**（§六），因此作为**唯一豁免场景**登记在 §六「全库一次性重排」例外条款里。

## 理由

篇幅约束本身是显然的（与定位一致），真正需要记录的是**为什么破例改存量**：

- **只对新批生效不够**：存量的 376 题才是用户实际刷的主体，若只约束新批，碎片化目标要到很久后才兑现。
- **追加式修订的代价不可接受**：走常规「新 questionId + `retiredQuestionIds`」意味着重写 376 题后，库里会残留同等数量的停用长题常驻（停用不可恢复），并使跨批重复/标签盘面失真；而重排的语义是「同一批题换形态」，不是「新增一批题」。
- **清库重导的代价可接受**：App 导入是追加式、不会更新已入库题目，故重排必须配一次「清空 App 数据 → 全量重导」。经实测，MuMu 上仅有 **1 条**作答记录——丢失代价可忽略。

## 代价与边界

- **§六「首版只追加」被开了一个口子**：因此例外条款写死四条硬要求——维护者发起 + 逐批留痕、重排后清库重导、重排期间冻结新批投放、**不得用于日常修订**（日常修订仍走新 ID + `retiredQuestionIds`）。没有这条例外，未来的读者会以为原地重写是违规操作。
- **程序题跌破 20% 到 10%**：绝大多数题不可运行验证，质量把关进一步压在「冷复审 + 来源核查」通道上——出题规范 §三「概念题三形态」「source 四档」是主要防线。
- **本决策是易逝的**：一旦全库重排完成、篇幅约束成为常态，这条 ADR 的历史价值就只剩「为什么当初敢破 only-append」这一条；篇幅数值本身若再变，走修订段而非新 ADR。
- **视觉与交互不变**：篇幅约束不引入任何 Schema 字段，App 侧除「清库重导」外零改动（与 [ADR-0011](./0011-difficulty-as-soft-rule-not-schema-field.md) 同取向——长度与难度都不建模为数据字段）。
