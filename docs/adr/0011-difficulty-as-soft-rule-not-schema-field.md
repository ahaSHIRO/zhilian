# 难度梯度走出题软规则，Schema 不设 difficulty 字段

题库受众从「维护者纯自用」扩展为「维护者 + 同学」（同学反馈现有题偏难，2026-09-30），「新手可刷性」成为出题侧真需求。对此本决策为：**难度不在数据模型建模**——不加 Schema 字段、不进 batch-check 机械校验，改由三处承载：

1. **批次主题天然分层**：协程/Flow 线题干偏难、空安全/基础线偏易，批次名即难度信号；练习筛选按分类选取即可构成新手路径（如从 batch-0002、batch-0009 刷起）。
2. **内容类型配比硬约束**（既有）：程序脑内执行题 ≤60%，认知负荷最重的题型被比例封顶。
3. **批内难度梯度软规则**（新增，出题规范 §三）：每批宜含 2–3 道入门题，程序题宜避免连续超过 2 道；仅「宜」，由验收体感把关。

> **修订（2026-10-04，内容类型配比改定）**：上面第 2 条引用的既有硬约束已由出题规范 §三 改定——
> **程序脑内执行题由「≤ 60%」改为「< 20%」，概念题相应由「≥ 40%」改为「> 80%」**；
> 且**只对改定之后新派单的批次生效，存量与在制批次（`batch-0001~0026`）一律不追溯**。
> **本决策的结论不变**（难度仍不建 Schema 字段、仍由上述三处承载）；变的是第 2 条的**数值**。
> 需要留意的连带效果：概念题升到 >80% 后绝大多数题不可运行验证，把关通道从「可运行验证」大幅转向
> 「复审 + 来源核查」——这与本决策「难度靠验收体感、不靠机械兜底」的取向一致，但也意味着**软规则承担的份额更重了**。
> 下面「理由」中引用的 `batch-0003 程序题涨到 80% 才被发现` 作为**当时的教训**保留，不回改判。

> **修订（2026-10-05，篇幅与配比再改定 + 全库重排）**：上面第 2 条的数值再次收紧——**程序题由 `< 20%` 改为 `≤ 10%`**，并新增**篇幅硬线**（题干去代码 ≤100 字、代码块 ≤1 个且 ≤6 行、题干含代码 ≤180 字、解析 ≤400 字、单选项 ≤60 字）；内容取向也改为**以基础/关键知识点为主**（定义/名词型题允许）。与 2026-10-04 那次不同，本次**追溯存量**：`batch-0001~0026` 已按 §六「全库一次性重排」例外条款全量重排达标。本决策的结论仍不变（**难度不建 Schema 字段**、仍由批次主题 + 配比 + 验收体感承载）；变的是第 2 条的数值与新增的篇幅维度。详见 [ADR-0016](./0016-question-brevity-hard-limits-and-full-bank-reflow.md) 与出题规范 §三。

## 理由

评估过三个备选：

- **Schema 加 difficulty 字段**（easy/medium/hard）：需同步动 batch-v1.schema.json、batch-spec-v1.md、App 实体与 batch-check 四处；且出题代理自评难度普遍失真（自己出的题自己觉得简单），字段一旦失真反而污染筛选与统计。收益（按难度筛选/统计）在 117 题规模下用分类筛选即可替代。
- **纯不做**：同学反馈证明难度问题真实存在，且既有教训表明「惯性」需要规则 counterbalance（batch-0003 程序题涨到 80% 才被发现）。
- **软规则**（采纳）：零迁移成本、可演进为硬规则、不引入失真数据。

## 代价与边界

- 软规则依赖验收体感，无机械兜底——这是有意的：难度是主观档位，机械拦截会产生大量误报与措辞博弈。
- **挂起重议条件**（满足其一即重开议题）：题库过 300 题；「新手套餐」类 App 需求成真；引入间隔重复（SRS）时难度是调度输入之一。
- App 侧**不做**新手入口改动：练习筛选已支持全维度（科目/分类/标签/题型），为个别新手用户预置筛选组合属过度设计。
- 本批既有 117 题不做难度回溯标注；存量「偏难」定性为结构问题（协程/Flow 占 kotlin 89%，塔基薄）而非质量问题，由后续基础线批次（集合/函数/Lambda/类与对象）补齐。
