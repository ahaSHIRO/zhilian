# 批次管理页 UI 归并：已处理批次退化为孤儿兜底，撤销限定为文件离场后

> 本决策是 [ADR-0008](./0008-batch-auto-discovery-and-manual-trigger.md)「单 `LazyColumn` 多 section」定案与 [ADR-0017](./0017-directory-authoritative-reconciliation.md)「目录为权威源」模型在 UI 层的收口：列表3「已处理批次」从常驻 section 退化为条件 section，撤销按钮的可用范围限定为「文件已不在目录的批次」。

**背景**：批次管理页自首版（`dc246fe`）就有两个列表——「目录中的批次文件」（SAF 实时扫描，瞬态）与「已处理批次」（Room `processed_batches`，持久），这是 [ADR-0001](./0001-sync-question-batches-not-database.md) 同步模型的结构性镜像（目录 vs 数据库两个数据源）。`f5c3189` 把双 `LazyColumn` 合并为单 `LazyColumn` 三 section（修滚动 bug，定案 ADR-0008）；`e346d7d` 实装对账（ADR-0017）后，目录文件列表升级为对账状态视角（五态着色），已处理批次列表承担撤销入口——但二者仍各自常驻。

这造成三个痛点：① 同一已对账批次在两个 section 重复出现（26 批全在目录时，列表2 26 行 + 列表3 又 26 行）；② 列表3 只渲染顺序号、不显示文件名，用户看不出两边的对应关系（关联键 `batchId` 未在 UI 标出，且 `ProcessedBatchEntity` 本有 `file_name` 字段却未渲染）；③ 撤销按钮埋在用户已当冗余信息忽略的列表3 行尾，可发现性极差。

更根本的矛盾：在 ADR-0017「目录为权威源、`ON_RESUME` 自动对账」模型下，文件还在目录时撤销是**矛盾操作**——撤销后下次回前台自动对账又把该批原样导回，撤销等于没做。撤销唯一**不矛盾**的场景是：电脑端已把 json 从目录移走，但手机本机的题与记录仍在，用户想清理手机端残留。这时撤销不是「反对电脑端」，而是「跟随电脑端删除做收尾」，与「电脑为主」理念自洽。

对此本决策为：

- **列表2「目录中的批次文件」为唯一主体**：每项 = 文件名 + 对账状态五态（`New`/`Reconciled`/`Stale`/`Blocked`/`ParseFailed`）；处理结果（`IMPORTED`/`PARTIAL`/`FAILED`）不再单独显示——在自动对账下 `IMPORTED` ≈ `Reconciled`、`PARTIAL`/`FAILED` 是会被下次 `ON_RESUME` 重试的瞬时态，其信息已被 `Blocked`/`ParseFailed` 与对账摘要卡覆盖。
- **列表3「已处理批次」退化为「目录中已无文件的已处理批次」条件 section**：只在存在孤儿批次（已处理但文件已不在目录）时渲染，平时不出现。每项 = 文件名 + 原处理时间 + 撤销按钮（error 色），按 `batchOrder` 倒序。26 批全在目录时该 section 不出现，重复消失。
- **撤销按钮只出现在孤儿 section 的项上**：文件还在目录的已处理批次，列表2 不挂撤销按钮（不置灰——置灰+提示会占视觉且暗示「有功能但用不了」，徒增困惑；靠「撤销只在孤儿 section 出现」的一致规则让用户自然理解「想撤销先去电脑端移文件」）。
- **撤销语义不变**：仍走 `BatchReconcileService.undoBatch`（整批删题+作答记录+待决+处理记录，文件不删），但因前置条件限定为「文件已不在目录」，撤销不会被下次自动对账重导抵消。
- **数据层无改动**：`undoBatch`、`FileState`、`fileState()`、`BatchFingerprint` 全部复用；本次只动 `BatchManageScreen` 的渲染与 section 组织。

## 理由

- **从「电脑为主」直接推出**：ADR-0017 已定目录为权威源、电脑端改题手机自动生效。手机端就不该有「擅自推翻电脑端」的写操作——文件还在目录时允许撤销，等于手机端能单方面剔除电脑端仍持有的批次，与权威源理念冲突。把撤销限定为「文件已不在目录」，撤销就从「反对电脑端」变成「跟随电脑端删除的收尾」，模型自洽。
- **消除重复与可发现性**：列表3 长期不出现，26 行重复消失；撤销只在该出现的地方出现，且语义清晰（电脑端删了文件→手机端清理），不再埋在被忽略的冗余列表里。
- **状态收敛降认知负担**：对账状态五态已涵盖用户该关心的「这批对账到哪一步」；处理结果是旧导入模型的遗留语义，在自动对账下价值衰减，收掉避免两套语义重叠区（`Reconciled` ∩ `IMPORTED`）造成的认知冗余。

## 代价与边界

- **撤销可用范围收窄**：文件还在目录时，手机端不再提供撤销。若用户想「撤销一个文件还在的批次」，必须先在电脑端把 json 从 Syncthing 目录移走，回手机端后该批进孤儿 section 才能撤销。这是有意边界，符合「电脑为主」——若要「手机端永久剔除某批连电脑端都不用动」，需新增「本机忽略名单」并修 ADR-0017 的「目录权威源、自动对账全覆盖」，**本决策不引入**该机制。
- **孤儿 section 非空时仍占篇幅**：但孤儿只在用户主动删过目录文件后出现，非常驻；26 批常态下页面只有列表2。
- **列表3 的「处理结果日志」视角消失**：`IMPORTED`/`PARTIAL`/`FAILED` 计数不再常驻可见。但 `PARTIAL`/`FAILED` 的失败信息已由对账状态 `Blocked`/`ParseFailed` 与对账摘要卡承载，不丢信息。
- **不改动对账模型与数据层**：本决策纯 UI 层，不动 ADR-0017 的对账规则、两阶段写入、指纹算法、`undoBatch` 实现。

## 与既有决策的关系

- **ADR-0008**：本决策是其「单 `LazyColumn` 多 section」定案的延续深化——「已处理批次」从常驻 section 退化为条件 section，方向一致，非重开议题。
- **ADR-0017**：撤销语义（`undoBatch`）不变，但新增 UI 层前置约束——撤销仅对文件已不在目录的批次开放。这是从 0017「目录为权威源」理念直接推出的、对撤销可用范围的限定。
