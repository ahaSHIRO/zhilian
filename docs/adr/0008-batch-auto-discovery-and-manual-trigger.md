# 批次自动发现与一键导入，明确不做后台静默入库

> **表述修订（2026-10-05）**：本文「入库仍是显式用户动作」的部分已被 [ADR-0017](./0017-directory-authoritative-reconciliation.md) **取代**——入库改为**打开 App 时自动执行的题库对账**（含同 ID 内容更新），批次页的按钮降为手动兜底。本文的**边界本身不变**：`发现自动`、`App 未打开时不做后台静默入库`（不引入 WorkManager/FileObserver），以及「疑似重复始终人工裁决」。（下文「考虑过的替代方案」中，**理由 1「人工触发是入库前的最后一道人为闸门」随之不再适用**——那道闸已由对账的自动应用替代；理由 2、3 仍成立。）

批次导入页改为「**进入/返回页面自动重扫目录 + 一键全部导入**」：Syncthing 同步进来的新批次无需退出重进即可看到（`ON_RESUME` 触发扫描），页面顶部「全部导入」按钮把所有未导入且无冲突的批次串行入库；Schema 失败、批次顺序号冲突等异常批次跳过并在汇总对话框逐批列出；**疑似重复题仍保持人工裁决**（与 ADR-0001 的导入韧性一致，不在批量流程里自动放过）。单批导入按钮保留。目录文件与已处理批次记录统一按 `batchOrder` **倒序**排列（最新批次在最上）。

> **顺带修复**：原页面在一个不可滚动的 `Column` 里并置两个无高度约束的 `LazyColumn`（目录文件、已处理批次），批次增多后整页无法滚动。现合并为**单个 `LazyColumn`**，待决重复 / 目录文件 / 已处理批次是同一列表的三个 section，整页连续滚动。

**考虑过的替代方案：后台全自动（不打开 App 也入库）。** 否决，理由有三：

1. **批次在电脑侧才是定稿点**。出题代理与维护者共用 `<出题交付目录>`，误投半成品、返工旧版到同步目录是真实会发生的事；人工触发是入库前的最后一道人为闸门，静默入库会让手机题库失去这道闸。
2. **疑似重复是刻意保留的人工决策**（README「导入韧性」）。后台流程遇到重复只能二选一：自动放过（破坏韧性）或挂起（那仍需用户打开页面处理，静默没有省掉任何动作）。
3. 个人单设备、批次节奏以天计，没有「App 长期不打开也必须及时入库」的场景；为此引入 WorkManager / FileObserver 常驻与 SAF 目录监听，复杂度不划算（项目当前无任何后台任务依赖）。

**后果**：「发现」是自动的（回页面即扫）；「入库」在本文成文时是显式用户动作（点单个导入或全部导入）——**该点已由 [ADR-0017](./0017-directory-authoritative-reconciliation.md) 取代为「打开 App 时自动对账」，手动按钮降为兜底**。本段仍成立的边界是：**App 未被打开期间新批次不会进入本机题库**。这是有意的边界，不是未完成的待办——不要把它当「自动检查尚未实现」再做一遍。
